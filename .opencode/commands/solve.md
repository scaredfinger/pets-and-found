---
description: Plan and solve one or more related GitHub issues, with one PR
---

Accept $1 as comma-separated issue numbers, $2 as optional base branch (default current branch), and $3 as maximum combined iterations (default 5). If missing $1 stop with a concise request.

Prime current operational guidance, available roadmap, and relevant category compactions as implementation context. Follow project governance and scoped branch guidance when reviewing conflicts and deciding what decision records to consult. Determine current package graph and semantic impact as far as existing tools allow.

Before starting services or running database-, browser-, or container-dependent work, load and follow the `devcontainer-runtime` skill. Use the project's documented preflight and recoverable setup before reporting an infrastructure blocker; report actual evidence. Unrelated tasks do not require this skill.

Before GitHub interactions, load and follow the `github-authentication` and `github-interaction` skills. If authentication or required authorization is unavailable, stop. On bootstrap do not assume package automation is already installed.

Create one combined plan with issue-by-issue acceptance criteria, semantic dependencies, test impact and minimal validation. Before creating a branch, load and follow the `branch-naming` skill. Use one branch for the combined issues, based on the selected base branch. Never discard unrelated worktree changes or force push.

Implement with a competent primary agent; use independent reviewer as available. Keep architecture docs/issue bodies out of delegated context unless necessary. Run the minimum relevant tests, lint and architecture evaluations **when implemented**. Iterate on actionable failures up to max iterations across local/CI/review. Never claim unimplemented checks passed.

Use the test command contract established by the project's applicable governance and scoped branch decisions. Under ADRs 00011 and 00016, run `pnpm test` for all unit tests and `pnpm e2e` for applicable project-owned end-to-end coverage. Where a reviewed adoption replaces that contract, use `pnpm test:all` and `pnpm e2e:all` instead. In either case, `pnpm test:arch` runs architecture tests and `pnpm test:cinderling` runs Cinderling-specific validations. During implementation run affected checks; before candidate review run the applicable all-unit-tests command, `pnpm test:arch`, and `pnpm test:cinderling`. Determine e2e applicability under project governance and scoped branch guidance; a missing or unconfigured command alone is not evidence that it is unnecessary. Where explicitly confirmed inapplicable, report the basis and not a pass; where required, arrange the applicable project-wide e2e command against the reviewed exact-head candidate after review and before merge, and report missing, unavailable or deferred evidence as pending or blocked. Report unclear applicability as unresolved. Any candidate change invalidates prior final-gate evidence; rerun the appropriate gates against the new head. Do not represent the starter adoption scenario as full project e2e. Existing consumers adopt changed contracts through reviewed migration.

Assess the scope for changes to governance, architectural rules, or agent workflow before implementation; create or update scoped draft ADRs when those rules change, reviewing their effects against relevant compactions and consulting decision history as needed for decision work. Keep the PR in draft while scoped unpromoted ADRs remain. A valid scoped draft is authoritative on its branch but not part of promoted architecture. Never edit accepted ADRs.

Before PR validate graph reachability/blast-radius assumptions, decision governance, no-comments policy, and behavior test coverage; note any checks not yet implemented. Before an authorized commit load and follow the `commit-naming` skill; commit only intended files with one Phoenix-Trigger trailer (unless bootstrap exception). Before creating the PR load and follow the `pr-creation` skill, validating the approved issue set and complete closing references immediately before creation and checking the persisted body afterward. Push and create one PR, do not merge. Observe CI against exact head SHA; if failing fix within retry limit, otherwise report blockers. Report branch, PR and validation state.

When a draft decision is in scope, distinguish its branch authority from promoted compactions. Require exact issue references in the PR and report incomplete acceptance without claiming it passed. Treat a release integration or fresh-host check as pending until it actually runs.
