# Clerk authentication across application boundaries

Use this skill when a project chooses Clerk and needs browser-to-BFF-to-API authentication. Inspect the project's architecture, Clerk SDK versions, session and authorization model, deployment URLs and existing tests first. Adapt to the installed SDK and current Clerk documentation rather than copying framework-specific calls blindly. Projects own their Clerk instance, JWT template, claim mapping, identity and authorization policy; this skill does not configure them or mandate Clerk for every consumer.

Before starting services or running browser-, database-, or container-dependent checks, load and follow `devcontainer-runtime`. Map browser-facing origins, BFF-to-API addresses, proxy buffering, cookies, TLS and Clerk redirect URLs from the actual runner and deployment topology; localhost in one network namespace is not another service's localhost. Keep secret keys server-side, use environment-specific configuration, and never log tokens or credentials.

Inventory the publishable key and JWT template name used by the browser, and the issuer, trusted JWKS URL, audience, role-claim path and authorized role used by the API. Name these settings for the consumer project and retain its existing secrets and configuration. Require explicit production values rather than allowing development defaults to satisfy a production presence check. Confirm the template actually emits the configured audience and role claims; treat a missing subject, claim or role as a failure.

## Browser and BFF

- Initialize the browser Clerk SDK with the appropriate publishable key. Wait for Clerk/session loading before deciding whether the user is signed out. Acquire a short-lived session JWT using the configured named API JWT template (for example, `getToken({ template: '<project-template>' })`) when making an authenticated request; handle null tokens and acquisition failures as unauthenticated, not as permission to proceed. Do not substitute a publishable key, secret key, session ID or a token with the wrong audience. Align template name, issuer, audience and claims with the API verification configuration.
- Send the token to the same-origin BFF in `Authorization: Bearer <token>` over TLS in deployed environments. The BFF validates request shape, extracts the bearer token and forwards it only to the configured trusted API origin for REST calls and streams. Reject missing or malformed authorization; do not accept user-supplied upstream URLs or forward credentials across redirects. Preserve method, relevant content types and upstream status, including 401 and 403, without exposing token values in logs or errors. Avoid storing tokens in URLs, persistent browser storage or cookies invented for this purpose.
- For SSE, native `EventSource` cannot set an Authorization header: use a fetch-based SSE client or another explicitly authenticated transport. Forward `Accept: text/event-stream`, bearer authorization and a validated `Last-Event-ID` to the API; stream bytes promptly without buffering, propagate cancellation/disconnect upstream, and handle proxy timeouts and backpressure. Do not put bearer tokens in query strings.
- Track the last successfully processed SSE event ID; reconnect with a newly acquired template token and `Last-Event-ID` when available, respecting server retry hints with bounded backoff and cancellation. Handle duplicate events idempotently, empty/reset IDs, expiry or 401 by refreshing once or returning to sign-in without a tight retry loop; treat 403 as authorization failure. Define replay retention and a resynchronization path when the cursor is too old or replay is unavailable. Do not claim exactly-once delivery.

## API verification, roles and identity

- Verify the JWT signature with trusted Clerk issuer keys using the supported SDK or a maintained JWT library; pin allowed algorithms, expected issuer and audience, and validate expiration and not-before with bounded clock skew. Use a configured issuer/JWKS endpoint, cache and refresh keys for rotation, fail closed on verification failure and never derive trust from unverified claims or a token-supplied key URL. Test missing, expired, tampered, wrong-issuer and wrong-audience tokens and key rotation.
- Map only verified claims to a stable principal keyed by issuer and subject (`sub`), not email or display name. Define user provisioning, account linking, deleted users and tenant/organization membership explicitly; do not trust client-supplied identity headers. Source roles and permissions from verified, server-controlled claims or an authoritative store, define tenant scope and default-deny missing or unknown roles. Enforce authorization on every API operation and stream subscription: 401 for absent/invalid authentication, 403 for an authenticated principal lacking permission. Do not treat UI hiding or BFF forwarding as authorization.
- JWT verification alone generally remains valid until expiry even after a Clerk session is revoked or roles change. Define acceptable staleness, short token lifetimes and, where immediate revocation is required, a server-side session/authorization check or revocation mechanism. Revalidate or terminate long-lived streams on expiry, revocation or permission change according to that policy; reconnect must acquire a fresh token and reauthorize. Test the chosen behavior rather than assuming offline JWT verification detects revocation.
- Give jobs and service-to-service callers separate machine credentials, identity, audience and least-privilege authorization policy. Never reuse a person's browser token, Clerk secret key or a shared development bypass as a machine identity. Verify machine credentials through their appropriate supported mechanism and keep secrets out of source, fixtures, logs and browser bundles.

## Redirects, recovery and evidence

Configure Clerk allowed origins and sign-in/sign-out redirects for each real browser-facing environment. Preserve a safe local return path through sign-in, reject external or protocol-relative return destinations, and avoid redirect loops. Handle loading, signed-out, expired session, denied permission and Clerk/network failures distinctly, offering retry or sign-in as appropriate without losing safe navigation state. Never silently turn verification or configuration failures into successful authentication.

Use deterministic test-only signed JWTs and isolated issuer/keys, mocked Clerk SDKs or explicit fixture verifiers to exercise browser acquisition, bearer forwarding, API verification, role denial, identity mapping, stream cancellation, reconnect and cursor replay, expiration and revocation policy. Constrain fixture mode to test configuration and prove production cannot enable a bypass; check both browser fixture injection and the API verifier's trusted keys. These fixtures do not verify a hosted Clerk login, actual JWT template, deployed redirects, browser cookies, proxy streaming or live revocation. When authorized credentials and a suitable environment are available, run a separate hosted browser sign-in and API/SSE exercise, including refresh/reconnect and sign-out/revocation behavior; report the environment, sanitized results and any unrun checks. Do not create accounts or change hosted configuration without authorization.

## Framework-specific illustration

In a SvelteKit browser client, initialize Clerk and request a named template token before calling a same-origin `+server` route. That route can forward the incoming bearer header to a configured Express API; it does not independently acquire the browser's token. An Express middleware can verify the JWT against configured issuer, audience and JWKS, require `sub`, resolve the configured role-claim path, and authorize before looking up the local user. Adapt SDK calls and middleware to the project; do not assume this example validates the BFF header or implements revocation automatically. Audit each REST and SSE proxy route for its header, status, redirect, cursor and cancellation behavior.

For a replayable stream, a project may retain change records and emit a reset when a cursor is invalid or too old; define how the client reloads a fresh snapshot after that reset and handles duplicate events. A subject-only local identity key assumes one trusted issuer; plan a mapping migration before changing or adding issuers. These are project-specific choices, not requirements to copy the sample's persistence model.
